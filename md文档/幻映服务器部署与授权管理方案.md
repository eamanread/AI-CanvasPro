# 幻映服务器部署与授权管理方案

> 日期：2026-05-21  
> 主题：幻映从本地单机工作台走向服务器部署时，授权管理、账号体系和数据库的改造判断

## 1. 结论先行

幻映当前更接近“本地单用户工作台”：前端是原生 Web 单页应用，后端是本地 Python 服务，用户数据默认写入本机目录，例如 `user/`、`data/`、`output/`、`user_data/`。

如果只是把幻映放到一台服务器上供自己或内部少量用户远程访问，部署难度中等，可以先做单用户服务器版。

如果要公开给很多用户在线使用，做成 SaaS 版幻映，难度会明显上升。此时不建议继续只依赖本地激活码，应该引入账号机制、数据库、用户隔离和后台授权管理。

推荐最终形成双模式：

```text
桌面版 / 本地版
  -> 继续支持本地激活码 / CDKEY / 设备绑定

服务器版 / 在线版
  -> 使用账号登录 + 数据库授权 + 后台管理
```

## 2. 服务器部署难度判断

### 2.1 单用户服务器版

适用场景：

- 自己使用。
- 公司内部少量人使用。
- 不需要严格的多租户隔离。
- 服务器只是替代本地电脑运行 `server.py`。

主要工作：

- 在服务器运行 Python 后端。
- 配置端口、防火墙、反向代理和 HTTPS。
- 处理静态资源访问。
- 指定稳定的数据目录。
- 给访问入口加一个简单登录或管理员密码。
- 控制外网访问安全。

难度：中等。

### 2.2 多用户 SaaS 版

适用场景：

- 面向多个用户开放。
- 每个用户有自己的项目、素材、输出结果。
- 需要会员、套餐、额度、到期时间。
- 需要后台管理和审计。
- 需要 AI 助手授权管理。

主要工作：

- 用户账号系统。
- 登录态和 token 管理。
- 数据库。
- 用户数据隔离。
- 文件存储隔离。
- 后台管理系统。
- 套餐和权限系统。
- 调用额度和审计日志。
- 并发任务和队列。

难度：较高。

## 3. 本地激活码是否还能用

本地激活码仍然适合桌面版和离线版。

适用场景：

- Windows EXE 本地运行。
- 单机授权。
- 设备绑定。
- 离线可用。
- CDKEY / MAC 绑定 / license 文件。

但如果幻映部署到服务器并开放给多个用户，本地激活码就不再适合作为主要授权方式。原因是：

- 服务器上所有用户共享同一个运行环境。
- 授权对象应该从“这台机器”变成“这个账号”。
- 需要区分不同用户的套餐、额度、项目和权限。
- 需要后台随时启停用户权限。

因此建议：

```text
本地版：继续保留激活码
服务器版：改为账号授权
```

## 4. 是否需要账号机制

如果只是个人服务器使用，可以先不做完整账号体系，只做管理员登录。

如果要给用户使用，需要账号机制。

账号机制至少要支持：

- 注册 / 登录。
- 密码哈希存储。
- 登录 token / session。
- 用户状态：正常、禁用、过期。
- 套餐状态：免费、试用、专业版、企业版等。
- 功能权限：是否允许 AI 助手、是否允许图像生成、是否允许视频生成。
- 设备绑定：如果需要桌面版和账号体系混合授权。

## 5. 是否需要数据库

服务器公开部署后，建议必须引入数据库。

数据库不是为了保存所有图片和视频，而是为了保存“归属关系、权限、状态和索引”。

图片、视频、项目 JSON 可以继续放在文件系统、对象存储、MinIO、OSS、S3 等位置。数据库保存它们属于谁、路径在哪里、是否可访问、什么时候创建。

最小数据库表可以包括：

```text
users
  用户账号、邮箱/手机号、密码哈希、状态、创建时间

sessions / tokens
  登录态、刷新 token、过期时间、设备信息

plans / subscriptions
  套餐、到期时间、助手权限、生成权限、额度

devices
  用户设备绑定、机器码、最后活跃时间

projects
  项目归属、项目名、项目文件路径、更新时间

assets
  上传素材归属、文件路径、类型、大小、创建时间

outputs
  生成结果归属、文件路径、生成来源、创建时间

assistant_usage
  AI 助手调用记录、消耗、错误、审计信息
```

## 6. 最大改造点：用户数据隔离

当前本地版默认是单用户路径：

```text
user/Canvas Project/
user/config.json
data/uploads/
output/
user_data/
```

服务器多用户版不能继续这样共享目录，否则会出现用户之间数据混用、误读、误删的问题。

服务器版应改成按用户隔离：

```text
storage/users/<user_id>/projects/
storage/users/<user_id>/uploads/
storage/users/<user_id>/outputs/
storage/users/<user_id>/settings/
```

或者使用对象存储：

```text
数据库记录用户和文件关系
实际文件放到 S3 / OSS / MinIO / 本地 storage
```

关键原则：

- 所有项目必须有 owner。
- 所有上传文件必须有 owner。
- 所有输出文件必须有 owner。
- 后端 API 不能只按路径读文件，必须先校验当前登录用户是否有权限。

## 7. 授权管理应该放在哪里

授权管理应该放在幻映自己的后端服务层，而不是前端，也不是 Claw / OpenHuman / 任何 AI 内核里面。

推荐新增或拆分这些服务：

```text
services/auth_service.py
  登录态、token、当前用户解析

services/account_route_service.py
  登录、退出、当前账号信息

services/entitlement_service.py
  套餐、功能权限、额度、到期时间判断

services/server_storage_service.py
  多用户数据目录和文件归属管理

services/assistant_auth_service.py
  AI 助手使用权限判断
```

需要保护的接口包括：

```text
/api/v2/projects/*
/api/v2/assets/*
/api/v2/workflows/*
/api/v2/assistant/*
/api/v2/proxy/*
/api/v2/runninghubwf/*
/api/v2/dreamina/*
/api/upload
/api/v2/save_output
```

## 8. AI 助手授权位置

如果后续接入 `claw-code` 作为 AI 助手，它不应该负责账号授权。

推荐调用链：

```text
前端助手面板
  -> /api/v2/assistant/chat
  -> 幻映后端检查用户登录
  -> 幻映后端检查套餐是否允许 AI 助手
  -> 幻映后端调用 claw.exe 或本地 agent runtime
  -> 返回回答
```

不要做成：

```text
前端助手面板
  -> claw-code 自己判断授权
```

原因：

- 授权属于幻映产品层，不属于 AI 内核。
- 将来换 AI 内核时，账号系统不应该重写。
- 幻映要控制是否允许读项目、改节点、执行工具、消耗额度。

## 9. 后台管理系统建议

如果要做正式商业化服务器版，建议把后台管理做成独立服务，而不是塞进本地客户端代码里。

推荐整体结构：

```text
huanying-local-app / huanying-web-app
  幻映前端
  Python 本地或服务器后端
  画布、项目、生成、AI 助手入口

huanying-admin-server
  用户管理
  登录注册
  套餐管理
  授权管理
  设备管理
  额度管理
  管理员后台
```

幻映客户端或服务器后端只需要向授权后台查询：

```text
当前用户是谁？
是否登录？
是否允许使用 AI 助手？
是否允许使用图像/视频/音频生成？
套餐是否过期？
额度是否足够？
```

## 10. 离线授权和在线账号如何并存

可以采用混合策略。

### 本地 EXE 版

- 使用本地 CDKEY。
- 绑定设备。
- license 文件本地保存。
- 可离线使用。

### 在线服务器版

- 使用账号登录。
- 数据库存储套餐和权限。
- 后台管理用户。
- 文件和项目按用户隔离。

### 混合授权

如果希望桌面版也支持账号登录，可以做成：

- 在线登录一次。
- 本地缓存授权 token。
- 允许离线使用 3 天、7 天或 30 天。
- 到期后要求重新联网校验。

本地授权缓存建议放在：

```text
user/assistant-auth.json
```

正式版本中不应明文保存敏感 token。Windows 可以考虑使用 DPAPI 做本机加密。

## 11. 推荐实施路线

### 阶段一：保留本地版

目标：不破坏当前用户。

- 本地激活码继续使用。
- Windows EXE 继续按本地工作台运行。
- 不急着改所有数据路径。

### 阶段二：服务器单用户版

目标：先验证服务器运行形态。

- 加管理员登录。
- 固定服务端数据目录。
- 配置 HTTPS 和反向代理。
- 验证项目保存、上传、输出、AI 助手调用。
- 可以先用 SQLite。

### 阶段三：多用户 SaaS 版

目标：正式商业化。

- 引入 PostgreSQL / MySQL。
- 用户账号体系。
- 用户数据隔离。
- 套餐和权限。
- 后台管理系统。
- 对象存储或隔离文件系统。
- AI 助手调用额度和日志。
- 任务队列和并发控制。

## 12. 最终建议

如果幻映只是个人或小团队远程使用，可以先做单用户服务器版，难度可控。

如果要公开给用户使用，建议不要继续使用本地激活码作为主授权方式，应该引入账号系统和数据库。

最推荐的长期架构是：

```text
本地桌面版
  本地激活码 / CDKEY / 设备绑定

在线服务器版
  账号登录 / 数据库 / 后台管理 / 用户隔离 / 套餐授权

AI 助手
  由幻映后端做授权网关
  Claw 等 AI 内核只做执行，不做商业授权
```

一句话总结：

> 服务器公开部署后，授权对象应从“机器”升级为“账号”；本地激活码保留给桌面离线版，服务器版需要账号体系和数据库。
